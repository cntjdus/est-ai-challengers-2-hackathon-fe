# 레시피 DB 연결

기존 Supabase 스키마를 사용합니다. 추가 마이그레이션이나 기존 데이터 초기화는 필요하지 않습니다.

## 연결 범위

- `recipes`: 목록, 제목, 설명, 기준 인분, 시간, 난이도, 출처, 태그
- `recipe_ingredients`: 필요량, 단위, 선택 재료 여부
- `recipe_steps`: step_no 순서대로 조리 안내
- `food_items`, `food_aliases`: 식재료 ID/이름/별칭으로 기존 냉장고 재고 매칭
- 홈과 냉장고 상세에서 DB 레시피로 이동. UUID 상세 주소 새로고침 지원
- 인분에 따른 보유량/부족량 계산 및 기존 재고 차감 RPC 연결

food_id가 있으면 그 ID를 우선 사용합니다. 없는 재고는 이름 또는 DB 별칭이 하나의 식재료로 확정되는 경우만 연결합니다. 같은 식재료라도 단위가 다르면 합산하지 않습니다. 단위 환산은 아직 적용하지 않았으며 g↔개수 등은 사용자에게 확인 필요로 표시합니다. 여러 구매 묶음의 차감은 기존 소비기한 우선 로직을 사용합니다.

## 데이터 준비와 한계

구현 중 조회한 운영 DB에는 레시피가 0개였습니다. 실제 데이터가 들어오기 전에는 빈 목록이 정상입니다. 샘플 레시피를 자동 삽입하지 않습니다. 각 레시피에는 food_items를 참조하는 recipe_ingredients와 recipe_steps가 필요합니다. 조리 도구 컬럼은 없으므로 미등록으로 표시합니다.

알레르기/비선호 제외 및 개인화 추천은 이 변경에 포함하지 않습니다. 장바구니 저장, 스크랩 영구 저장도 별도 작업입니다. 상세 화면에서 저장 없이 '담김'만 표시하던 임시 버튼은 보유량/부족량 표시로 대체했습니다.

기존 프로젝트의 authenticated SELECT 권한과 RLS 읽기 정책을 확인했습니다. 운영 사용자 재고, DB 스키마, 레시피 데이터는 변경하지 않았습니다.

## 검증

- Vitest 33개 통과, Vite 빌드 성공, oxlint 통과
- DB 응답을 대체한 통합 테스트: 수정 → 재조회 → 화면 재생성 후 유지, 확인 후 폐기 → 목록 복귀
- 레시피 UUID 직접 진입, 인분별 부족량, 빈 DB, 조회 오류와 재시도 검증
- 별칭/ID 매칭, 중복 재료 합산, 단위 불일치, 여러 구매 묶음 차감 검증
- 실제 브라우저 로그인 후 운영 DB에서 수정/폐기/차감한 결과는 아직 검증하지 않았습니다.

## 적용 후 확인

1. 기존 Supabase 환경변수로 앱을 실행합니다.
2. 관리자가 확인한 레시피와 식재료/조리 순서 데이터를 등록합니다.
3. 레시피 목록 → 상세 → 새로고침 시 같은 레시피가 표시되는지 확인합니다.
4. 같은 식재료/단위로 냉장고에 등록한 재고와 인분별 필요량을 비교합니다.
5. 테스트용 재료에서만 수정/폐기/요리 차감 후 재로그인하여 유지 여부를 확인합니다.
