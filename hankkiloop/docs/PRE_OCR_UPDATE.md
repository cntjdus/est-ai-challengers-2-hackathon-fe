# 한끼루프: 장바구니부터 OCR 전 단계까지

## 적용 순서

1. 실행 중인 개발 서버를 Ctrl+C로 종료하고 기존 hankkiloop 폴더를 백업합니다.
2. Supabase SQL Editor에서 이 ZIP의 hankkiloop/docs/shopping_setup.sql 전체를 실행합니다.
3. ZIP의 hankkiloop 폴더 내용을 기존 hankkiloop 폴더에 같은 경로로 덮어씁니다.
   이 파일은 전체 프로젝트가 아닌 변경 파일 패치입니다. 기존 package.json, .env, 이미지 파일은 유지합니다.
4. PowerShell에서 실행합니다.

   cd "C:\Users\우성한\Downloads\est-fridge-app\hankkiloop"
   npm run dev

5. 브라우저에서 강력 새로고침합니다. 예전 장바구니 히스토리는 복원하지 않습니다.

SQL은 설치 스크립트로 제공되며 운영 DB에는 아직 실행하지 않았습니다.
기존 레시피 10종, 이미지, 사용자 재고를 삭제하거나 초기화하지 않습니다.
사용자별 기존 RLS를 유지하고, 새 함수는 SECURITY INVOKER 및 authenticated 전용 실행 권한을 사용합니다.
재고 수량 수정 권한을 추가로 개방하지 않습니다.

## 이번 변경

- 예시 대파·두부·계란 장바구니 제거. 실제 DB가 비어 있으면 빈 목록을 표시합니다.
- 로그인 사용자별 장바구니 조회와 선택 상태·수량 변경·삭제 저장.
- 레시피 상세에서 인분에 맞춘 필수 재료를 담습니다. 선택 재료는 자동 담기에서 제외합니다.
- 같은 레시피의 미완료 장바구니는 중복 생성하지 않습니다. 다시 담으려면 기존 품목을 모두 삭제하거나 구매 등록하세요.
- 여러 레시피를 담을 때 미완료 장바구니에 배정한 보유량을 다시 배정하지 않습니다.
- 구매 완료 → 실제 구매량·보관장소·소비기한 확인 → 냉장고 등록.
- 냉장고 등록, 소비기한 저장, 장바구니 구매 완료를 하나의 DB 트랜잭션으로 처리합니다.
- 같은 구매를 재시도하거나 새로고침 후 재전송해도 냉장고에 중복 입고하지 않습니다.
- 기존 요리 완료·선택 재료 차감 기능을 유지합니다. 재고가 없는 재료는 차감하지 않으며 오래된 재고부터 차감합니다.
- 기본 인분에서 보유한 재료 비율과 선호 태그로 규칙 기반 추천 순서를 계산합니다. 모델 호출은 사용하지 않습니다.
- 알레르기·비선호 재료를 홈, 목록, 상세 주소, 재료별 추천, 메뉴 알림에서 제외합니다.
- 실제 정보가 없는 소포장 상품·매장 데모 화면 진입을 차단합니다.

## 계산·알레르기 제한

- 장바구니는 담을 당시 재고의 스냅샷입니다. 이후 냉장고를 수정하거나 요리하면 자동으로 구매량을 재계산하지 않습니다.
- 상품 API가 없으므로 표시하는 것은 실판매 상품·가격이 아닌 식재료와 구매 예정량입니다.
- +/−는 최초 부족량의 배수입니다. 예: 부족량 60g → 2배는 120g.
  실제 100g을 구매했다면 냉장고 등록 화면에서 100g으로 조정하세요.
- 구매가 완료된 계획은 재고 배정을 해제합니다. 구매 후 미래의 식사까지 예약·관리하는 식단 스케줄러는 아닙니다.
- 현재 장바구니 스키마는 g/ml/ea(개)를 지원합니다. 다른 단위는 추측해서 바꾸지 않고 안내합니다.
  이번 패치는 품목별 g↔개 환산 데이터를 추가하지 않습니다.
- 알레르기 필터는 이름·키워드 기반의 보조 기능입니다. 계란/달걀 등 별칭과 두부·간장·된장 등 일부 가공 재료를 보수적으로 처리하지만,
  제품별 숨은 성분, 교차접촉, 모든 별칭과 사용자 자유 입력을 완전히 판별하지 못합니다.
  안전한 식사임을 보장하지 않으므로 반드시 실제 포장 성분표를 확인하세요.
- 알레르기 설정을 바꾸어도 이미 저장한 장바구니를 자동 삭제하지 않습니다. 기존 구매 목록은 직접 다시 확인하세요.

## 직접 확인할 순서

1. SQL 적용 → 장바구니 처음 열기: 빈 목록, 예시 상품 없음.
2. 부족 재료가 있는 레시피 상세 → 인분 설정 → 장바구니 담기.
3. 장바구니의 이름·단위·구매량 확인 → 새로고침 후 유지 확인.
4. 수량 변경·선택 해제 → 새로고침 후 유지, 선택 삭제 확인.
5. 장보기 완료 → 실제 소비기한·보관장소·구매량 입력 → 등록.
6. 냉장고에 새 재료가 있고 장바구니에서 빠졌는지 확인.
7. 같은 레시피 요리 완료 → 사용할 재료 선택 → 차감 후 새로고침.
8. 다른 계정 로그인 → 이전 계정 장바구니·재고가 보이지 않는지 확인.
9. 마이페이지에서 계란 알레르기 저장 → 달걀 레시피가 목록과 직접 상세 주소에서도 제외되는지 확인.

## 검증

프런트: npm test, npm run lint, npm run build.
SQL: tests/validate-shopping.cjs를 별도 PGlite 테스트 DB에서 실행.
tests/fixtures/shopping-schema.sql은 운영 테이블 정의만 복사한 테스트용 스키마로, 운영 데이터는 포함하지 않습니다.
SQL 테스트는 반복 설치, RLS 계정 격리, 보유량 중복 배정 방지, 수량 충돌,
구매 등록 롤백·재시도, 구매 원본 연결, 계획 완료·취소, 비로그인 거부를 검증합니다.
이 테스트는 실제 브라우저 로그인부터 운영 DB까지의 최종 사용자 테스트를 대체하지 않습니다.

## 아직 제외한 부분

OCR 인식, 실제 AI 채팅 호출, 실판매 소포장·매장 API, 스크랩 DB 영구 저장,
알림 읽음 상태의 DB 저장·푸시 알림은 이번 범위에 포함하지 않습니다.
이 기능의 기존 화면이 있다고 해서 백엔드 연결까지 끝난 것은 아닙니다.
